# Реальные данные Bitrix → Codex → чат

Уточнение: обычная статистика выполняется локально функцией get_employee_statistics. Она получает задачу и историю Bitrix, считает числа, сохраняет отчёт; не получает тексты результатов, не маскирует данные и не обращается к Codex. Поэтому вопрос об отправке при запросе статистики появляться не должен. Облачный анализ содержания работ — отдельная функция analyze_employee_work (API kind=employee_review), её нужно явно запросить. Вопрос по данным содержит название задачи, найденные фрагменты и выбор словами: «нет» исключает только эту задачу из облачного анализа с отметкой в отчёте, «Продолжить» отправляет показанную версию. Номер задачи пользователю вводить не требуется.

Сводка статистики содержит completed_tasks и current_tasks — отдельные списки с key/title и, для Bitrix, url. Модель перечисляет названия выполненных и текущих задач, просроченные показывает только числом counts.overdue. Исходные массивы ключей в полном отчёте сохраняются для проверки расчёта. Для старых отчётов без названий используются метаданные sources или ключ задачи; модель не должна выдумывать название.

После обновления сервиса переподключите MCP и начните новый чат. В рабочем MCP теперь четыре функции: resolve_employee, get_employee_statistics, analyze_employee_work, privacy_decision. Параметры подключения остаются прежними. Для локальной статистики сервис не зависит от готовности контейнера Codex; зависимость healthcheck в Compose снята.

Этот режим заменяет демонстрационный источник. Qwen вызывает фиксированную функцию статистики; сервис получает видимые задачи Bitrix и историю, локально рассчитывает показатели, маскирует текст и передаёт проверенные материалы Codex CLI. Codex поясняет работу по данным Bitrix, сервис восстанавливает имена и сохраняет отчёт, Qwen получает числа, пояснение и ссылку. Числа не вычисляются моделью.

Это анализ задач сотрудника за период по Bitrix. GitLab, Kaiten, чтение вложений и сравнение отчёта с кодом в этот режим не включены. Произвольные вопросы о портале, изменение задач и выполнение команд не предоставляются модели.

## 1. Подготовка

Остановите старый демонстрационный сервис через Ctrl+C: он занимает порт 8000. Docker Desktop и приложение с Qwen должны быть запущены.

В PowerShell:

```powershell
cd C:\Users\Azaliya\coding\ai
python tools/prepare_bitrix_live.py --registry data/docker-test/registry.sqlite
```

Команда создаёт отдельную рабочую папку data/bitrix-live и один раз копирует существующий справочник через SQLite backup. Оригинал не изменяется; повторный запуск не перезаписывает рабочий справочник или настройки. Если ваш настоящий справочник расположен иначе, укажите его путь внутри data. Дальше добавлять/редактировать сотрудников нужно в рабочем справочнике:

```powershell
python -m employees --db data/bitrix-live/private/registry.sqlite list
python -m employees --db data/bitrix-live/private/registry.sqlite edit EMP_001
```

У выбранного сотрудника должен быть настоящий Bitrix ID. Заполните ФИО, варианты имени, почты, телефоны и логины: они используются для маскировки текста всех сотрудников, встречающихся в материалах. Не оставляйте демонстрационную запись вместо настоящего человека.

## 2. Вебхук и сборка

В том же терминале укажите свой вебхук. Секрет хранится в окружении процесса, не в коде и не в MCP:

```powershell
$env:BITRIX_WEBHOOK_URL = 'https://ВАШ-БИТРИКС/rest/ID/СЕКРЕТ/'
docker compose -f compose.bitrix.yaml build
```

Перед первым реальным запросом можно проверить новые части в Linux-контейнере на вымышленных данных:

```powershell
docker build -t ai-service .
python tools/run_bitrix_checks.py
```

Сценарий не передаёт контейнеру вебхук, справочник или авторизацию Codex. Проверяет локальный Bitrix, обезличивание, подставной CLI и настоящий Unix-сокет. Тест MCP пропускается, если в основном Python-образе нет Node.js; его полный маршрут отдельно проверен на Windows с установленным Node.js.

Новый Compose запускается отдельным файлом, прежняя офлайн-конфигурация не изменена. Версия Codex закреплена 0.166.0, совпадает с обнаруженной установленной CLI. Другая проверенная версия задаётся CODEX_VERSION перед сборкой. CODEX_MODEL по умолчанию равен default: Codex использует модель своей установленной версии и учётной записи. Разработчик может закрепить доступную модель через окружение CODEX_MODEL; через чат модель не меняется.

## 3. Отдельный вход в Codex по подписке

```powershell
docker compose -f compose.bitrix.yaml up -d codex-gateway
docker compose -f compose.bitrix.yaml run --rm --no-deps codex --login
```

CLI покажет ссылку и код входа. Откройте ссылку в браузере, войдите в свой аккаунт и подтвердите код. Дождитесь успешного завершения команды. При необходимости разрешите device-code login в настройках аккаунта ChatGPT. Доступность Codex и лимиты зависят от аккаунта. Этот вход не использует API-ключ и не копирует домашний каталог установленного Codex.

Авторизация хранится в отдельном Docker-томе codex-auth. Сервис не видит этот том; Codex не видит data, справочник, вебхук, Docker socket и настройки Codex на хосте. Не выполняйте down -v, если хотите сохранить вход.

Проверка входа:

```powershell
docker compose -f compose.bitrix.yaml run --rm --no-deps codex --login-status
```

Перед повторным входом при уже работающем анализаторе сначала остановите его: docker compose -f compose.bitrix.yaml stop codex. Вход и анализ не должны одновременно менять файл авторизации.

## 4. Запуск

```powershell
docker compose -f compose.bitrix.yaml up -d
docker compose -f compose.bitrix.yaml ps
docker compose -f compose.bitrix.yaml logs -f --timestamps service codex
```

Терминал с logs можно оставить открытым. Ctrl+C останавливает просмотр, контейнеры продолжают работать. Дождитесь healthy у codex и service. Порт сервиса публикуется только на 127.0.0.1:8000. Файл токена читается из data/bitrix-live/local-token.txt.

Codex не имеет сетевого интерфейса, кроме loopback. Обмен с сервисом идёт через выделенный Unix-сокет, а доступ к провайдеру — через отдельный CONNECT-шлюз. Шлюз допускает только api.openai.com, chatgpt.com и auth.openai.com на 443 с публичными IP. Если версия CLI требует другой адрес, вход/анализ завершится ошибкой; список не расширяется автоматически. Фактическая работа device login и CLI sandbox в вашей Docker-среде требует проверки. При несовместимости изоляция не отключается.

## 5. Переключение MCP

Откройте:

```powershell
notepad data\bitrix-live\mcp-entry.json
```

В Settings → MCP измените существующий employee-worklog. Command — значение command из файла. Arguments — каждое значение массива args в отдельной строке:

1. C:\Users\Azaliya\coding\ai\mcp-bridge\server.mjs
2. --address
3. http://127.0.0.1:8000
4. --token-file
5. C:\Users\Azaliya\coding\ai\data\bitrix-live\local-token.txt
6. --enable-privacy

Request timeout установите 1900 секунд. Сохраните настройки и переподключите MCP. Доступны resolve_employee, get_employee_statistics и privacy_decision. Последняя функция предназначена только для явного решения пользователя по остановленной задаче; модель получает инструкцию не принимать это решение самостоятельно.

## 6. Первый реальный запрос

Выберите прошедший небольшой период и человека из рабочего справочника, например:

```text
Используй employee-worklog. Покажи статистику Хакимьяновой Азалии
с 2026-10-23 по 2026-10-31 и пояснение Codex по данным Bitrix.
Укажи пропуски, ограничения и ссылку на полный отчёт.
```

Проверьте исходные задачи в Bitrix, числа, пояснение и ссылку. В полном отчёте source_mode должен быть bitrix, demo — false, analysis_kind — bitrix_statistics_with_codex. Появление пояснения в analyses и этапов codex/restore подтверждает прохождение анализатора; один Connected этого не подтверждает.

Если остались персональные данные, отправка останавливается. Модель должна показать находки и предложить «Продолжить», «Очистить», «Пропустить». Продолжить разрешает отправку показанной версии как есть; Очистить заменяет первое найденное значение и повторяет проверку; Пропустить исключает материал задачи из анализа. Молчание не запускает Codex. Количественная статистика по подтверждённой истории сохраняется отдельно от пропущенного качественного анализа.

Блокируется только проблемный материал: проверенные задачи продолжают анализироваться в Codex. В чате показывается одна ожидающая задача; одно решение относится только к её task_id и версии. Для следующей задачи нужен новый ответ пользователя. При продолжении уже полученные результаты используются повторно без нового обращения к Codex. В waiting-ответе доступны analyzed_task_ids, checked_task_ids, skipped_task_ids и progress; окончательный отчёт сохраняется после обработки всех решений. Команда не должна считаться выполненной без подтверждения decision_applied. В журнале её применение видно по privacy_decision с task_id и action.

## 7. Полный журнал и отчёты

Постоянный журнал этапов каждого запуска: data/bitrix-live/logs/<run_id>.jsonl. Включает UTC-время, run_id, задачу, этап, начало/успех/ошибку. Тексты задач, авторизация и найденные персональные данные в журнал не записываются. Рабочие материалы сохраняются до решения по данным, после завершения запроса удаляются. Полный отчёт сохраняется постоянно в data/bitrix-live/reports/<run_id>/report.json. Ссылка просмотра действует 10 минут; сам отчёт не удаляется.

Последний журнал:

```powershell
Get-ChildItem data\bitrix-live\logs\*.jsonl |
    Sort-Object LastWriteTime -Descending |
    Select-Object -First 1 |
    Get-Content -Encoding UTF8
```

Сохранение консольных логов Docker без оформления stderr как ошибки PowerShell:

```powershell
python tools/bitrix_logs.py
```

Файл: data/bitrix-live/docker.log. Журнал всех этапов лежит отдельно в logs; сырой вывод модели и секреты туда не включаются. Ошибки CLI намеренно выдаются обобщённо; вход проверяется через --login-status.

Остановка с сохранением данных и авторизации:

```powershell
docker compose -f compose.bitrix.yaml down
```

## Ограничения исторических данных

При массовых пропусках normalize запустите из корня проекта:

```powershell
python tools/diagnose_bitrix.py 54 100 1782
```

Используйте номера проблемных задач из вашего журнала. Пересборка контейнера для этой команды не требуется; скрипт читает Bitrix из существующего ai-service-1 и сохраняет безопасную структуру в data/bitrix-live/diagnostics/task-<id>.json. В выводе показывается точная известная причина нормализации. Содержимое задач, результаты и имена не сохраняются; аккаунты заменяются вымышленными ID. Codex не вызывается. Улучшения основного журнала вступают в силу после пересборки service.

Сервис перебирает все видимые вебхуку задачи, созданные до конца периода, чтобы не потерять переназначенные задачи. Это может занять время. Защитный предел — 1000 задач в config.json; превышение останавливает запуск, не выдавая обрезанный список за полный.

История должна содержать событие создания, последовательные изменения исполнителя/статуса/сроков и совпадать с текущими значениями. Неподтверждённые задачи пропускаются, итог помечается частичным. Лимиты страниц, ошибки доступа, удалённые задачи и неполнота журнала Bitrix не могут быть исправлены моделью. Даты ISO и Unix timestamp поддержаны; старый формат без пояса трактуется как согласованный UTC+5. Тексты, изменённые после конца периода, и поздние отчёты не используются как исторические доказательства.

Время записи NEW может быть позже createdDate. Оно не обязано совпадать точно: начало подтверждённой истории сохраняется как history_valid_from. Периоды после этой границы рассчитываются по восстановленным значениям; периоды, затрагивающие неизвестный начальный промежуток, отмечаются частичными. Ранняя, повторная или находящаяся после других изменений запись NEW отклоняется.

Каждая подходящая задача анализируется отдельным вызовом Codex. Длинный запрос может выполняться дольше ожидания чата (30 минут); уже запущенная работа продолжится, повтор того же запроса во время выполнения вернёт тот же запуск. Один материал свыше 200000 символов пропускается с отметкой частичного результата; разбиение одной большой задачи пока не реализовано. Сводка для Qwen ограничена 8000 символов, полный текст сохранён в отчёте. После аварийного перезапуска running помечается interrupted и временные данные удаляются; автоматического повторного обращения к Codex нет. Ожидание решения по данным сохраняется.

Официальная документация: [запуск Codex без интерфейса](https://learn.chatgpt.com/docs/non-interactive-mode), [авторизация](https://learn.chatgpt.com/docs/auth), [список задач Bitrix](https://apidocs.bitrix24.com/api-reference/tasks/tasks-task-list.html), [история Bitrix](https://apidocs.bitrix24.com/api-reference/tasks/tasks-task-history-list.html).
