# Локальный анализ работы сотрудников

Обычная статистика через get_employee_statistics выполняется полностью локально, без обезличивания, облачного ИИ и вопросов об отправке. Качественный анализ содержания работ через Codex вызывается отдельно: analyze_employee_work. Только в этом режиме проверяется исходящий текст и при необходимости задаётся вопрос по названию конкретной задачи; ответ «нет» исключает её из облачного анализа с отметкой в отчёте.

Реализованы справочник сотрудников, маскировка текста, статистика, отчёты и MCP для Bionic/LM Studio. Добавлена цепочка реального Bitrix: сбор задач и истории → локальный расчёт → маскировка → Codex → восстановление имён → ответ и отчёт. Проверка с тестовым Bitrix и подставным CLI прошла; настоящий Codex в Docker ещё нужно проверить. Инструкция запуска — [BITRIX_LIVE.md](BITRIX_LIVE.md). Kaiten/GitLab пока доступны отдельными выгрузками, сравнение кода с отчётом не реализовано. Точный статус — в [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md), решения — в [DECISIONS.md](DECISIONS.md).

Основная среда эксплуатации — Linux. Разработка и текущие проверки выполняются на Windows; фактический запуск на Linux ещё не проверен.

Пошаговые ручные проверки с вымышленными данными: [MANUAL_TEST_PLAN.md](MANUAL_TEST_PLAN.md).

Без доступа к Bitrix/GitLab/Kaiten: [выбранные автономные проверки и генерация данных](OFFLINE_TEST_PLAN.md).

## Запуск на Linux

Нужен Python 3.10 или новее; рекомендуется Python 3.13, на котором сейчас проходят проверки. Из корня проекта:

```bash
python3 -m employees add
python3 -m employees list
python3 -m employees edit EMP_001
python3 -m employees import ./employees.csv
python3 -m unittest discover -s tests -v
```

Для постоянного пути базы можно установить `EMPLOYEES_DB` или передать `--db` перед названием команды:

```bash
python3 -m employees --db /path/to/local-data/registry.sqlite list
```

Пользователь, запускающий команды, должен иметь права записи в каталог базы. При переносе SQLite копируйте базу после завершения всех команд записи. Для Docker используется Linux-образ; на Windows Docker Desktop должен работать в режиме Linux-контейнеров. Файл `.gitattributes` закрепляет окончания строк LF для запускаемых файлов и конфигурации контейнера.

## Запуск в PowerShell

Нужен Python 3.10 или новее; проверено на Python 3.13. Внешние библиотеки устанавливать не нужно. Выполняйте команды из папки проекта:

```powershell
cd C:\Users\Azaliya\coding\ai
python -m employees add
python -m employees list
python -m employees edit EMP_001
python -m employees import .\employees.csv
```

`add` последовательно спрашивает ФИО, варианты имени, ID Bitrix, ID Kaiten, логин GitLab, почты автора коммитов, другие почты, телефоны и логины. Списки вводятся через `|`. Обязательны ФИО и хотя бы один аккаунт: ID Bitrix/Kaiten, логин GitLab или почта автора коммитов. Остальные поля можно заполнить позже. Числовые ID должны быть положительными целыми числами.

После добавления выводится постоянная метка `EMP_001`. Сотрудники не удаляются. Метку нельзя задать или изменить самостоятельно.

В `edit` пустой ввод оставляет текущее значение; `-` очищает поле. Нельзя очистить ФИО или все аккаунты одновременно. Прежние значения сохраняются в истории для дальнейшей маскировки; прежний аккаунт нельзя незаметно выдать другому человеку. Если запись изменилась, пока вы вводили ответы, сохранение остановится с просьбой открыть редактирование заново.

`list` показывает краткую таблицу. Все поля и историю можно посмотреть командой:

```powershell
python -m employees list --json
```

По умолчанию база создаётся в `data/private/registry.sqlite` относительно текущей папки. Для другого пути используйте параметр **перед командой**:

```powershell
python -m employees --db C:\LocalData\registry.sqlite list
```

Альтернатива — переменная окружения `EMPLOYEES_DB`. SQLite и CSV содержат локальные данные сотрудников, поэтому папка `data` исключена из Git и Docker build context.

## Импорт CSV

Скопируйте [employees.template.csv](employees.template.csv) в `employees.csv` и добавьте строки. Кодировка UTF-8, допустим BOM; разделитель столбцов — запятая, списков внутри ячейки — `|`. При сохранении из Excel убедитесь, что выбран разделитель-запятая: точка с запятой не поддерживается этой версией.

```csv
full_name,aliases,bitrix_id,kaiten_id,gitlab_username,gitlab_emails,emails,phones,logins
Иванов Иван Иванович,Иванов И.И.|Иван Иванов,123,456,ivanov,ivanov@example.test|i.ivanov@example.test,,,
Петров Пётр,,234,,petrov,petrov@example.test,,,
```

Это вымышленные примеры; замените их реальными данными. `full_name` обязателен, остальные столбцы можно опустить, но каждая запись должна иметь хотя бы один аккаунт. Не добавляйте столбец метки: её генерирует приложение.

Перед записью команда показывает новых сотрудников, существующие записи и ошибки. Сохранение выполняется только после `да`, `yes` или `y`. Другой ответ отменяет импорт; конец ввода/Ctrl+C также ничего не сохраняет.

- Совпадение аккаунта и известного ФИО означает существующую запись: она пропускается без изменений. Новые поля из такой строки тоже не добавляются — используйте `edit`.
- Совпавший аккаунт с другим ФИО, аккаунты разных людей в одной строке и повтор аккаунта среди новых строк — ошибка.
- Одинаковые ФИО с разными аккаунтами допустимы: это могут быть разные люди. Определить одного человека без общего аккаунта автоматически нельзя — проверьте список до импорта.
- При ошибках ни одна новая строка не сохраняется. При записи аккаунты повторно проверяются в одной транзакции: конфликт не оставляет половину импортированного списка.
- Логины GitLab и почты автора сравниваются без учёта регистра. Для ID ведущие нули не создают другой аккаунт: `00123` и `123` считаются одним ID.

## Docker

Добавлена конфигурация только для справочника. Docker должен быть установлен отдельно; в текущем окружении его нет, поэтому сборка и запуск контейнера здесь не проверены.

```powershell
docker compose up -d --build service
docker compose exec service employees add
docker compose exec service employees list
docker compose exec service employees edit EMP_001
```

Контейнер не запускает HTTP-приложение: он ожидает команды справочника. Сетевой доступ отключён. Папка `./data` подключается как `/data`; база внутри контейнера — `/data/private/registry.sqlite`. Поэтому локальные команды из корня проекта и контейнер используют одну и ту же базу.

Для импорта поместите файл в `data/employees.csv`, затем выполните:

```powershell
docker compose exec service employees import /data/employees.csv
docker compose down
```

Остановка и пересоздание контейнера не удаляют `data`. CSV после импорта не удаляется автоматически: это введённый пользователем файл, а не временный файл анализа.

## Проверка

```powershell
python -m unittest discover -s tests -v
```

Проверки запускают настоящие команды отдельными процессами с временными базами. Настоящую базу сотрудников они не читают и не изменяют. Проверяются постоянство меток, история редактирования, конфликты, подтверждение импорта, отмена, ошибки CSV и одновременные изменения. Отдельных тестов внутренних функций или SQL-таблиц нет.

Коды завершения: `0` — успешная команда или явный отказ от импорта; `1` — ошибка данных/хранилища; `2` — неправильные аргументы; `130` — прерывание или незавершённый ввод.

## Локальная маскировка текста

Сначала заполните справочник. Варианты имён добавляйте явно: например, фамилию, инициалы и распространённые написания с е/ё. Склонения и любые неизвестные имена автоматически не распознаются.

```powershell
python -m privacy prepare task.txt --run-dir data/work/privacy-demo
python -m privacy inspect data/work/privacy-demo
python -m privacy export data/work/privacy-demo --output data/outbound.txt
python -m privacy restore data/work/privacy-demo answer.txt --output data/reports/report.txt
```

Родительский каталог выходного файла должен существовать. Для другой базы укажите `--db` перед командой. Каталог запуска создаётся новым: существующий не перезаписывается. Весь каталог запуска приватный; не отдавайте его анализатору. Только результат `export` предназначен для дальнейшей передачи.

Замена учитывает текущие и исторические значения справочника, границы слов, регистр и распространённое форматирование телефона. При неоднозначном имени или неизвестном контакте статус становится `awaiting_privacy_decision`. `prepare`/`inspect` показывают совпадения и причину только локально; выгрузка блокируется.

```powershell
python -m privacy decide data/work/privacy-demo continue --version <версия-из-inspect>
python -m privacy decide data/work/privacy-demo skip --version <версия-из-inspect>
```

`continue` разрешает передать конкретную показанную версию с оставшимися данными; `skip` запрещает выгрузку. Изменённый после проверки файл не выгружается по старому разрешению. Команды не обращаются в облако. Для повторной очистки пока исправьте исходный текст и создайте новый запуск через `prepare`; автоматическое действие «Очистить локальной Qwen» ещё не подключено.

`restore` подставляет имена из снимка конкретного запуска; неизвестные метки останавливают сохранение. Существующий отчёт не перезаписывается. Входные служебные метки `EMP_...` помечаются как `LITERAL_EMP_...` и требуют решения, чтобы их не спутать с метками, созданными программой.

Для JSON-ответа используйте `restore ... --json`: имена восстанавливаются в строковых значениях с правильным экранированием. Для анализатора есть `export ... --bundle`, который передаёт текст, разрешённые метки и идентификаторы источников, но не локальный маппинг. Протокол, запуск и ограничения описаны в [runner/README.md](runner/README.md). Реальных облачных вызовов в этой сессии не было.

Регулярные выражения дают эвристическую проверку почт/телефонов, а не обнаружение всех персональных данных; длинная числовая последовательность может потребовать ручного решения. Маскировка файлов PDF/DOCX и кода не выполняется в соответствии с принятыми исключениями. Автоматическая очистка временных файлов относится к завершённым запросам приложения; отдельные диагностические запуски privacy пока хранятся локально для проверки и не считаются завершённым запросом приложения.

## Статистика и постоянные отчёты

Прямой расчёт по JSON с нормализованной историей:

```powershell
python -m worklog statistics examples/tasks.json --employee EMP_001 --start 2026-10-01 --end 2026-10-31
```

`examples/tasks.json` — вымышленная история, не выгрузка вашей компании. Каждая задача имеет `key`, `created_at`, `history_complete` и массив событий `events`. События: `assignment` с меткой сотрудника, `status` со значением open/in_progress/completed, `deadline` со сроком либо null. Все даты событий должны содержать часовой пояс. Нельзя помечать непроверенную историю `history_complete: true`: при false задача отмечается недоступной для точного расчёта.

Сохранение запроса, выполнение и просмотр результата:

```powershell
python -m worklog --config examples/config.json start --employee EMP_001 --start 2026-10-01 --end 2026-10-31
python -m worklog process <run_id>
python -m worklog status <run_id>
python -m worklog report <report_id>
```

Сотрудник EMP_001 должен существовать в вашем справочнике. Конфигурация примера содержит `demo: true`, поэтому демонстрационный характер сохраняется в отчёте и краткой сводке. Для настоящей нормализованной истории укажите свой `source_file` в локальном файле конфигурации. Относительный путь считается от файла конфигурации, а не от папки терминала. Настройку источника задаёт разработчик, не модель.

Состояния запросов хранятся в `data/private/runs.sqlite`, отчёты — в `data/reports/<report_id>/report.json`, журнал этапов — в `data/logs/<run_id>.jsonl`. Временные файлы завершённого запроса удаляются. Отчёты не удаляются. Одинаковый активный запрос возвращает прежний run_id; после завершения можно создать новый.

Счётчики считаются локально, облачного пояснения сейчас нет. Текущая реализация повторно открытой задачи: если на конец периода она открыта, она текущая, а не завершённая. Нарушение срока учитывается один раз по первому нарушению; перенос срока после нарушения его не скрывает. Статистика по проекту пока отдельно не фильтруется.

## Локальный HTTP-интерфейс

Сначала задайте разработческий токен длиной не менее 16 символов. Например, в PowerShell:

```powershell
$env:WORKLOG_TOKEN = python -c "import secrets; print(secrets.token_urlsafe(32))"
python -m worklog --config examples/config.json serve --port 8000
```

В Linux используйте `python3` и задайте `WORKLOG_TOKEN` через окружение процесса. Приложение слушает только `127.0.0.1`. Заголовок подключения: `Authorization: Bearer <WORKLOG_TOKEN>`. Пользовательских ролей нет; это технический секрет локального подключения, а не выбор модели.

- `GET /health` — проверка работы.
- `GET /employees?query=Иванов` — минимальные кандидаты: имя и метка.
- `POST /analysis` — строго поля kind=employee_statistics, employee_id, start, end.
- `GET /analysis/<run_id>` — этап, состояние, краткая сводка и ссылка на отчёт.
- `GET /reports/<report_id>` — полный JSON с токеном подключения.
- `GET /view/<report_id>?expires=...&ticket=...` — выданная приложением ссылка на один HTML-отчёт, действует 10 минут. Текст экранируется, скрипты не исполняются.

Фоновый обработчик автоматически забирает запросы из очереди. MCP-переходник ожидает статус и получает только сводку/ссылку. Подключение Bionic и демонстрационный запуск описаны в [mcp-bridge/README.md](mcp-bridge/README.md). SDK LM Studio, npm install и lms dev больше не требуются. Проверена вся цепочка MCP-процесс -> локальный HTTP -> статистика на вымышленных данных; выбор инструментов самой Qwen в интерфейсе Bionic ещё требует проверки.

HTTP-режим сейчас проверен на Windows вне Docker. Текущая Compose-конфигурация запускает контейнер команд справочника без сети, а не HTTP-приложение. Не публикуйте встроенный локальный HTTP-сервер в интернете. Восстановление запроса, прерванного аварийным завершением процесса, ещё не реализовано; статус running после такого сбоя требует доработки восстановления, а не автоматического повтора анализа.

## Пакетная проверка основного контейнера

После `docker compose build` выполните из корня проекта:

```powershell
python tools/run_docker_checks.py
```

Сценарий выполнит 24 проверки на вымышленных данных в одном контейнере без сети. Существующие базы не используются. В конце выводятся `DOCKER_CHECKS_SUMMARY` и путь к отчётам в отдельной папке `data/docker-checks-*`. Повторный запуск создаёт новую папку. Ошибка теста возвращает ненулевой код завершения. Пакет проверяет основной контейнер; отдельные CLI-анализаторы и шлюз требуют дополнительных проверок.

## Прямые выгрузки источников

Рабочая цепочка Bitrix → Codex CLI → чат и отдельный Docker-запуск описаны в [BITRIX_LIVE.md](BITRIX_LIVE.md). Подготовка: python tools/prepare_bitrix_live.py --registry data/docker-test/registry.sqlite. Офлайн-демонстрация и прежний compose.yaml сохранены. Новая конфигурация — compose.bitrix.yaml; для подписки используется отдельный вход внутри контейнера, а не настройки Codex на компьютере.

Настройки разработчика — по образцу [examples/integrations.json](examples/integrations.json). Подставьте ваши адреса; секреты задавайте через указанные переменные окружения. Адрес Bitrix webhook включает секрет, поэтому предпочтителен `BITRIX_WEBHOOK_URL`, а не запись адреса в общий файл.

```powershell
python -m integrations --config data/integrations.json bitrix-task 123 --output data/bitrix-task.json
python -m integrations --config data/integrations.json kaiten-card 234 --output data/kaiten-card.json
python -m integrations --config data/integrations.json gitlab-changes --employee EMP_001 --project group/project --since 2026-10-01T00:00:00+05:00 --until 2026-11-01T00:00:00+05:00 --output data/gitlab-changes.json
```

Результаты этих команд **сырые, локальные и не обезличены**. Не отправляйте их в облако. Bitrix получает задачу, итоговые результаты и события истории, не чат. Kaiten получает карточку и явно настроенное свойство отчёта; без настройки сообщает not_configured. GitLab получает коммиты по точным почтам автора из справочника и изменения, отмечая неполные diff. `until` — исключительная верхняя граница.

Внешние HTTPS-запросы выполняются только по настройке разработчика; HTTP разрешён только для локальных тестов. Переадресации не выполняются, чтобы не передавать секреты другому адресу. Пользователь подтвердил получение реальной задачи Bitrix 1782. Для Bitrix добавлены преобразование истории и связь с очередью; для Kaiten/GitLab это ещё не реализовано. Скачивание и чтение файлов отчётов остаётся следующим этапом. Новый Docker-запуск и реальный Codex должны быть проверены отдельно, прежде чем считать цепочку готовой к эксплуатации.
