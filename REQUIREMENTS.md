# Требования к локальному сервису анализа работы

Статус: основные требования согласованы; это описание целевого поведения, а не заявление о полной готовности. Текущая реализация и ограничения перечислены в `IMPLEMENTATION_STATUS.md`, инструкции — в `README.md`, автономные решения разработчика — в `DECISIONS.md`. Исходная идея сохранена в `idea.txt`; при расхождениях этот документ отражает последующие решения. Будущие доработки перечислены в `FUTURE_FEATURES.md`.

## Цель и границы первой версии

Один пользователь задаёт вопросы о работе сотрудников через чат LM Studio. Локальная Qwen выбирает фиксированную функцию сервиса и её параметры. Сервис собирает данные из Bitrix, Kaiten и GitLab, считает показатели, подготавливает материалы для анализатора и возвращает результат.

Все три источника нужны в первой версии. Разграничение прав пользователей не требуется. Архитектура должна позволять добавлять функции, источники и способы запуска анализатора.

Основная среда эксплуатации — Linux. Текущая разработка и проверки выполняются на Windows. Код справочника должен работать на обеих ОС без изменения логики; пути к данным задаются конфигурацией. Docker использует Linux-контейнеры. Успешные проверки Windows не считать подтверждением фактической работы на Linux.

## Сценарии

### Статистика сотрудника за период

Пример: «Оцени продуктивность Иванова с 1 по 30 октября».

- Количество выполненных задач, задач с просрочкой и текущие задачи рассчитывает локальный код.
- Запрос обычной статистики не вызывает облачный анализатор, не требует обезличивания и не показывает вопрос о разрешении отправки. Качественный облачный анализ вызывается отдельной функцией по соответствующему запросу пользователя.
- Выполненные — завершённые в запрошенные даты включительно.
- Просроченные — задачи, срок которых нарушили именно в выбранном периоде. Задачи, уже просроченные до начала периода, в это число не входят. Учитывать историю изменения сроков, чтобы перенос не скрывал нарушение.
- Текущие — незавершённые на конец запрошенного периода.
- В ответе статистики отдельно перечислять названия выполненных и текущих задач; просроченные показывать только количеством, без отдельного списка. Если задача одновременно текущая и просроченная, она остаётся в списке текущих и учитывается в количестве просроченных.
- Для всех запросов и отчётов использовать единый часовой пояс Asia/Yekaterinburg (UTC+5). Даты источников приводить к нему при определении дней и периодов; отдельные часовые пояса сотрудников не настраивать.
- Выводы сопровождаются источниками. Количественные показатели не подменяются произвольной оценкой модели.
- Причина отсутствия, включая больничный, сохраняется в передаваемом контексте, если получена из источников. Источник этих сведений ещё предстоит определить.

### Анализ задачи или работы по проекту

Примеры: «Сравни отчёт и код по задаче 123»; «Какую работу проделал Иванов по проекту X за период?».

- Сервис получает постановку задачи, результаты работы и изменения кода сотрудника.
- Для проектного отчёта за период включать все задачи, где сотрудник был исполнителем хотя бы один день периода, в том числе назначенные ранее; наличие коммитов или отчёта в периоде не является условием включения.
- Для запроса за период использовать состояние на его конец: более поздние коммиты, отчёты и завершение не использовать. Более ранний код допустим как контекст, но не считается работой в выбранном периоде.
- Ссылка на репозиторий GitLab размещается в описании задачи в едином формате, например `GitLab: https://gitlab.example.com/group/project`.
- Принято допущение, что ссылки не содержат персональных данных; отдельную подмену ссылок и путей для обезличивания в первой версии не добавлять.
- Принято допущение, что номер задачи однозначен среди подключённых источников. Уточнение системы по совпадающим номерам не требуется; источник сохраняется во внутренних записях.
- Отчёт содержит описание реализованной функции либо перечень изменённых файлов с пояснениями. Точные ссылки на коммиты не обязательны.
- Если репозиторий невозможно определить из описания, задачу пропустить с объяснением. Прежнее требование обязательной ссылки на коммит в отчёте отменено.
- Не обходить весь чат задачи. Получать именно результаты/отчёты, прикреплённые при завершении, даже если они также отображаются в чате.
- Формы отчёта: текст с файлом, только файл, только текст. Несколько результатов рассматривать совместно, сохраняя даты и авторство.
- Поддерживать текстовые файлы, DOCX и PDF с извлекаемым текстом. Сканы и неподдерживаемые форматы отмечать как недоступные для анализа.
- Если приложенный отчёт прочитать не удалось, написать: «Отчёт приложен, но прочитать его не удалось; сравнение с отчётом не выполнено», указать причину и пропустить задачу целиком. Остальные задачи продолжить проверять. Это отличается от отсутствия отчёта, когда допускается анализ кода относительно постановки.
- Коммиты брать от первого фактического перехода задачи в работу до завершения, но для запроса за период не позднее конца этого периода. Для незавершённой задачи — до конца запрошенного периода. Не ограничивать начало коммитов началом периода отчёта, если задача началась раньше.
- Для завершённых задач получать отчёт независимо от того, завершены они раньше срока или с просрочкой. Просрочку показывать отдельно.
- При отсутствии отчёта анализировать код относительно постановки задачи, явно отмечая, что сравнение с отчётом не выполнялось.
- Отбирать коммиты по репозиторию, сотруднику и интервалу; связь уточнять по файлам и описанию функции.
- При неоднозначности писать: «Возможно параллельное выполнение задач; не все изменения удалось однозначно связать с этой задачей». Не утверждать параллельную работу как установленный факт. Выводы строить по подтверждаемым изменениям.
- Для утверждений отчёта показывать подтверждающие изменения либо отсутствие подтверждения. Итог: подтверждено, частично подтверждено, подтверждение не найдено. Отсутствие подтверждения не считать доказательством отсутствия работы.
- Передавать весь необходимый код. При превышении контекста анализировать частями и сводить результат; неполноту получения или обработки отражать явно.

## Архитектура

1. LM Studio работает на компьютере пользователя с локальной Qwen.
2. Bionic/LM Studio подключается к фиксированным функциям сервиса через локальный MCP-переходник (stdio). Это согласованная замена прежнего Tools Provider. MCP применяется только для связи чата с сервисом; обращения сервиса к Bitrix, Kaiten, GitLab и анализатору остаются прямыми API/CLI-вызовами. Переходник не предоставляет произвольные команды, пути к файлам, URL или доступ к справочнику целиком.
3. Сервис запускается в Docker и напрямую обращается к API Bitrix, Kaiten, GitLab через отдельные модули интеграций.
4. Сервис собирает данные, рассчитывает показатели, маскирует обрабатываемый текст, выполняет проверку, формирует запрос к анализатору.
5. Анализатор получает только подготовленные материалы. Сервис восстанавливает имена по меткам в ответе и сохраняет полный отчёт.
6. В LM Studio возвращаются статус, короткое резюме и локальная ссылка на полный отчёт. Отдельный чат не разрабатывается.

Названия бизнес-функций уточнить при реализации: статистика сотрудника за период; анализ задачи; анализ работы сотрудника по проекту и периоду. Параметры проверяет сервис, а не только промпт модели.

## Способы запуска анализатора

- Поддержать API облачной модели, автоматический запуск Codex CLI и автоматический запуск Claude Code как взаимозаменяемые способы выполнения анализа.
- Конкретный способ, поставщика и модель задаёт разработчик в конфигурации. Пользователь не меняет их через чат.
- Материалы отправляются выбранному анализатору; рассылка одновременно нескольким не требуется.
- Автоматического переключения на другого поставщика при ошибке нет.
- Codex/Claude Code запускаются в изолированном окружении с подготовленными материалами. У них нет доступа к справочнику, исходным выгрузкам и токенам систем-источников. Сам по себе отдельный рабочий каталог не считается достаточной изоляцией.
- Конкретная модель и способы аутентификации ещё не выбраны.

## Маскировка и принятые исключения

- Локальный справочник связывает людей, аккаунты и постоянные метки `EMP_001`, `EMP_002` и т. д.
- В обрабатываемом тексте заменять ФИО, известные варианты имён, логины, почты и телефоны по справочнику и правилам.
- Перед отправкой проверять остатки известных имён и логинов. При обнаружении остановить отправку конкретной задачи, локально показать найденные персональные данные, место обнаружения и причину. Не отправлять эти фрагменты облачному анализатору до решения пользователя.
- Вопрос об отправке показывать только в облачном сценарии и с названием задачи: «В задаче „название“ остались персональные данные. Отправить её в облачный ИИ?». Пользователь отвечает словами; ID и версию текущей задачи передаёт клиент. Ответ «нет» исключает только эту задачу из облачного анализа; отчёт содержит название и причину исключения. «Продолжить» разрешает отправку показанной версии как есть. Остальные проверенные задачи продолжают обрабатываться.
- Предоставить три действия: «Продолжить» — отправить как есть, включая показанные персональные данные; «Очистить» — передать проблемный фрагмент локальной Qwen, применить исправление и повторить проверку скриптом; «Пропустить» — пропустить эту задачу и продолжить остальные.
- При успешной повторной проверке продолжить обработку; при повторном обнаружении данных снова запросить решение. Молчание не является разрешением отправки. Разрешение «Продолжить» относится только к конкретной задаче и показанной версии материалов, не отключает проверку других задач или новых данных.
- Маппинг не передавать анализатору. Qwen получает готовые результаты и сведения, необходимые для уточнения пользователя; полный справочник и исходные выгрузки ей не выдаются.
- Настоящие имена авторов отчётов и коммитов и соответствия аккаунтов хранятся в локальной БД. В облако передавать постоянные метки сотрудников; имена подставлять локально только в готовый ответ.
- Для показа обнаруженных персональных данных и действия «Очистить» Qwen разрешается получать необходимые проблемные фрагменты локально; это исключение из правила выдачи только готового результата, а не доступ к полным выгрузкам или справочнику.
- Причины отсутствия сотрудника не скрывать по принятому решению пользователя.
- Для кода GitLab принято допущение об отсутствии персональных данных и токенов: код не очищать.
- Для файлов отчётов принято допущение об отсутствии персональных данных: содержимое вложений в первой версии не маскировать. Локальное извлечение текста для чтения/подготовки не означает проверку персональных данных.
- Поэтому нельзя заявлять гарантированное отсутствие всех персональных данных во всём исходящем материале. Проверка первой версии распространяется на обрабатываемый текст с указанными исключениями.

## Выполнение, ошибки и лог

- Пользователь вводит запрос, видит «В процессе», затем получает результат. Проверки состояния выполняются автоматически, без ручного ввода идентификаторов.
- Внутренний идентификатор запуска отличать от идентификатора задачи трекера.
- Повторный одинаковый запрос во время выполнения возвращает состояние текущего запуска, не создаёт копию анализа.
- Ошибка отдельной задачи не останавливает остальные: результат помечать как частичный, указывать пропуски и причины.
- Ошибка общего подключения, не позволяющая получить список задач, останавливает запуск. Ошибка анализатора возвращается пользователю без смены поставщика.
- Лог разработчика: название этапа и «этап завершился успешно» либо «этап остановлен: причина». Не сохранять секреты или исходные документы в сообщениях об ошибках.
- Этапы включают получение задач, получение отчётов, получение кода, подготовку и проверку текста, анализ, восстановление имён, сохранение результата.

## Справочник сотрудников

- Хранить локально в SQLite; файл базы находится в постоянной папке, подключённой к Docker. Пересоздание контейнера не удаляет справочник.
- Управлять командами терминала, без страницы и без изменения через чат.
- Данные: ФИО и варианты написания, идентификаторы Bitrix и Kaiten, аккаунт GitLab, используемые автором коммитов почты, известные логины/почты/телефоны для маскировки, постоянная метка.
- Новый сотрудник добавляется интерактивной командой: последовательные вопросы и сохранение. Метку назначает сервис автоматически и не выдаёт повторно другому человеку.
- Массовая загрузка — CSV по шаблону. До сохранения показывать новые записи и ошибки, проверять дубликаты. Существующие записи автоматически не перезаписывать; изменения — отдельной командой.
- Предусмотреть команды добавления, импорта, просмотра и редактирования. Удаления сотрудников нет.
- Если фамилия соответствует нескольким людям, сервис возвращает варианты, Qwen уточняет выбор, затем вызывает функцию с уникальным идентификатором. Неоднозначные соответствия аккаунтов не угадывать.

Команды справочника реализованы. Локальный запуск — `python -m employees`; Docker-конфигурация подготовлена, но запуск контейнера в текущем окружении не проверен. Инструкция и шаблон CSV — в `README.md`. Пример команд после запуска контейнера:

```powershell
docker compose exec service employees add
docker compose exec service employees import /data/employees.csv
docker compose exec service employees list
docker compose exec service employees edit EMP_001
```

## Хранение результатов

- Полные отчёты хранить локально постоянно. Не удалять их автоматически или при очистке временных данных; удаление отчётов приложением в первой версии не предусматривать.
- Временные файлы, включая скачанные исходники, материалы локальной проверки и обмена с анализатором, удалять после завершения всего запроса: успеха, частичного результата, окончательной ошибки или отмены. Сначала сохранить готовый отчёт, если он сформирован, и итоговый статус. Исходные файлы в Bitrix, Kaiten и GitLab не удалять.
- Ожидание решения по персональным данным не является завершением запроса: до решения или отмены его временные материалы сохранять. При аварийном прерывании сначала зафиксировать прерванное состояние запуска, затем удалить его временные файлы при следующем старте. Без ответа пользователя материалы в облако не отправлять.
- Постоянный справочник и метки хранить отдельно от временных материалов и не предоставлять окружению анализатора.

## Критерии готовности первой версии

- Оба сценария работают из чата LM Studio со всеми тремя источниками.
- Показатели воспроизводимо рассчитываются локально; анализ кода содержит ссылки/привязки к подтверждающим источникам.
- Проверены задачи с отчётом и без него, несколько результатов, поддерживаемые вложения, неоднозначные коммиты и частичные ошибки.
- Известные идентификаторы в обрабатываемом тексте заменяются; оставшиеся известные имена/логины останавливают отправку до решения пользователя. Проверены «Продолжить», локальная очистка с повторной проверкой и «Пропустить»; без ответа отправки нет. Исключения для кода и вложений сохранены явно.
- Имена восстанавливаются локально. Анализатор не получает справочник и доступ к исходным системам.
- Есть индикатор выполнения, результат, лог этапов и защита от повторного запуска.
- Работают команды справочника и проверяемый импорт CSV без автоматического перезаписывания существующих сотрудников.
- Конфигурация поддерживает API, Codex CLI и Claude Code; пользователь не выбирает анализатор. Доступность каждого проверяется с настроенной разработчиком учётной записью.

## Технические проверки до реализации соответствующих частей

Это проверки возможностей, а не уже работающие свойства системы:

- Версия/тип установки Bitrix, доступность API результатов и файлов; корректное разрешение идентификаторов вложений. В обычном REST `tasks.task.result.list` возвращает текст и `files`; REST 3.0 использует `result.items` и поле `fileIds`.
- Где именно Kaiten хранит используемый командой итоговый отчёт и как отличить его от остальных файлов/комментариев без обхода всего чата.
- Наличие истории статусов и дедлайнов в обоих трекерах; получение первого фактического начала работы и исторического состояния на конец периода.
- Сопоставление проектов между трекерами, исключение двойного учёта, если одна работа представлена в обоих источниках.
- Источник причин и длительности отсутствия сотрудников.
- Полнота GitLab diff: обработка лимитов, пропущенных файлов и больших изменений; сопоставление авторства коммитов с локальным справочником.
