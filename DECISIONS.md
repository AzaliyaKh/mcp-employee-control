# Вопросы и принятые решения

## Нужны ли обезличивание и разрешение для обычной статистики?

Нет. Пользователь уточнил: обычные числа рассчитываются локально без облака, поэтому для них не нужны маскировка и вопрос об отправке. Предыдущее объединение статистики с Codex было ошибочным. Разделены API kinds employee_statistics и employee_review и MCP-функции get_employee_statistics / analyze_employee_work. Пользователь не выбирает ID задачи вручную: облачный вопрос показывает название и найденные данные, клиент подставляет task_id/version. «Нет» означает отказ от облачной отправки только показанной задачи, она отмечается в отчёте как не рассмотренная. «Продолжить» разрешает показанную версию. Настройки анализатора остаются у разработчика.

## Как собрать первую реальную цепочку Bitrix и использовать подписку Codex?

По запросу пользователя реализован режим статистики сотрудника с пояснением Codex по Bitrix. GitLab/Kaiten и сравнение кода пока не включаются. Числа считает локальный модуль, модель поясняет только подтверждённые материалы. Просматриваются все доступные вебхуку задачи до конца периода, чтобы не потерять переназначенные; ограничение 1000 останавливает сбор вместо незаметного усечения. Неподтверждённая история даёт пропуск с причиной. Изменённые после среза тексты исключаются.

Codex запускается в отдельном контейнере без сетевого интерфейса и данных приложения. Подготовленные материалы поступают по выделенному Unix-сокету. Для подписки добавлен отдельный device login в Docker-том; домашний каталог и auth.json хоста не копируются. CONNECT-шлюз допускает только публичные адреса api.openai.com, chatgpt.com, auth.openai.com:443. Модель по умолчанию выбирается установленной версией Codex; разработчик может закрепить CODEX_MODEL, пользователь через чат — нет. Версия CLI 0.166.0 взята из фактически установленного codex --version. Новый запуск требует ручной проверки Docker, так как агент не имеет доступа к Engine.

Рабочий справочник однократно копируется через SQLite backup в data/bitrix-live, исходная база не меняется. Все дальнейшие изменения вносятся в рабочую копию. Действия по данным привязаны к задаче и версии; clean заменяет первое найденное значение и заново проверяет весь материал. Ожидающие материалы сохраняются, законченные очищаются; running после перезапуска становится interrupted без автоматического повтора анализа.

## Как подключить чат после отказа от прежнего Tools Provider? (3 ноября 2026)

По выбору пользователя используется MCP stdio-переходник между Bionic и локальным HTTP-сервисом. Это изменение касается только интерфейса чата: Bitrix, Kaiten и GitLab остаются прямыми API-интеграциями. Переходник предоставляет поиск сотрудника и статистику, не предоставляет оболочку, чтение произвольных файлов или произвольные HTTP-запросы. Используется установленный Node.js без npm-зависимостей. Конфигурация генерируется внутри проекта; настройки приложения пользователь добавляет через Settings → MCP. Автоматически проверены протокол и локальная HTTP-цепочка, работа интерфейса Bionic требует отдельной проверки.

Пользователь разрешил автономно выбирать этапы, проверки и решения в рамках проекта, без отдельных подтверждений. Изменения разрешены только внутри рабочей папки. Документ фиксирует решения разработчика; фактическая проверка внешних подключений указывается отдельно.

## Как продолжать TDD без подтверждения перед каждым тестом?

Следовать последнему указанию пользователя: самостоятельно выбирать публичные интерфейсы и записывать их в планы проверок. Проверять поведение, а не внутренние таблицы. Согласованные правила работы с персональными данными не отменяются этим разрешением на разработку.

## Какие этапы идут дальше?

Завершить локальную маскировку, затем реализовать локальный конвейер запросов и постоянные отчёты, затем подключаемые источники/анализаторы и интерфейс для LM Studio. Реальные подключения без настроенных адресов и учётных данных не выполнять; использовать явно обозначенные локальные примеры и тестовые серверы.

## Что означает «Продолжить» при разработке без подключённого облака?

Разрешение на выгрузку конкретной версии подготовленного текста, а не фактическую отправку. Команда export проверяет версию и состояние. Разрешение работать автономно не является разрешением отправлять обнаруженные персональные данные вместо пользователя.

## Где проверять работу?

Сейчас Windows/Python 3.13. Основная эксплуатация — Linux. Использовать переносимые пути и стандартную библиотеку там, где она достаточна; Docker и Linux не объявлять проверенными, пока фактически не запущены.

## Что делать с неизвестной меткой в ответе анализатора?

Не угадывать имя и не сохранять отчёт как успешный: сообщить неизвестные метки. Использовать локальный снимок имён конкретного запуска, а не изменяющийся справочник.

## Какой HTTP-фреймворк используется сейчас?

Для первого локального интерфейса — стандартная библиотека Python: внешние пакеты в окружении отсутствуют, а интерфейс обслуживает одного локального пользователя. Он слушает только 127.0.0.1, требует технический токен и не предназначен для публикации в интернете. Рекомендация FastAPI из обсуждения не была обязательным требованием. При дальнейшем развитии можно заменить транспорт, сохранив бизнес-операции.

## Как учитывать повторно открытые задачи?

Для первой реализации статистики смотреть состояние на конец периода. Повторно открытая и не закрытая к концу периода задача считается текущей, а не завершённой. Просрочка — первое нарушение срока задачи в выбранном периоде; повторное открытие не создаёт вторую задачу и не дублирует её счётчик. Изменения дедлайна после уже наступившей просрочки её не скрывают.

## Можно ли считать карточку источника полной историей?

Нет. Первые прямые выгрузки сохраняются отдельно от нормализованного массива для статистики. Bitrix отдаёт карточку, результаты и релевантные события истории; Kaiten — карточку и явно настроенное свойство отчёта. Пока исходное состояние и полнота истории не проверены, не устанавливать history_complete=true и не выдавать точную историческую статистику на основании текущей карточки.

## Где искать отчёт Kaiten?

Не угадывать по сообщениям чата. Разработчик указывает report_property_id, только если команда действительно хранит отчёт в соответствующем свойстве карточки. Без настройки возвращать not_configured, а не «отчёта нет». Файловое значение свойства пока помечается unsupported. Это временное ограничение прямой выгрузки, а не заявление, что все отчёты Kaiten устроены именно так.

## Как сопоставить коммиты GitLab с сотрудником?

Использовать точное совпадение почты автора со списком gitlab_emails и его историей в справочнике. Логин GitLab сам по себе не подтверждает авторство коммита. Если почты не заполнены, остановить сбор с понятной причиной. Интервал коммитов — от since включительно до until исключительно. Признаки too_large/collapsed означают частичную выгрузку; отсутствие этих признаков не доказывает отсутствие серверных лимитов.

## Как открывать отчёт из чата без передачи общего токена модели?

Выдавать временную подписанную ссылку на один отчёт сроком 10 минут. Общий WORKLOG_TOKEN остаётся в настройках приложения и плагина. Страница отчёта экранирует содержимое и не исполняет HTML/скрипты из данных. Истечение ссылки не удаляет сам отчёт.

## Как реализован первый анализатор и почему CLI пока не запускаются?

Первый adapter использует совместимый текстовый протокол Chat Completions, без инструментов. Весь локальный протокол проверяется с тестовым сервером; реальных облачных запросов не было. Позднее добавлены CLI-адаптеры и отдельный Docker runner: теперь их можно выбрать конфигурацией. Логика проверена подставными процессами; реальное выполнение и изоляция на целевом Linux ещё требуют проверки. Подробности ниже и в analyzer/README.md.

## Что проверяет контроль версий конверта?

Совпадение SHA-256 позволяет обнаружить изменение текста после локальной проверки/решения пользователя. Конверт создаёт доверенный код; это не защита от владельца компьютера, который сознательно подделал и текст, и хеш. Внешний анализатор не получает функцию создания такого разрешения.

## Как проверяются доказательства в ответе модели?

На первом текстовом этапе SOURCE_001 — целый переданный документ. Проверяются формат ответа, допустимые метки, существование ссылок и наличие источника у подтверждённого утверждения. Это не доказывает семантическую правильность вывода; привязка к коммитам и строкам кода остаётся следующей частью task_review.

## Как предотвращается утечка ключа через ошибки HTTP-библиотеки?

HTTP-ошибки нормализуются до короткого сообщения без URL, заголовков и тела ответа. Отдельный тест использует некорректный синтетический ключ с переводом строки и проверяет, что он не появился в stdout/stderr.

## Кому засчитать завершение после переназначения задачи?

Исполнителю на момент перехода в completed. Последующее переназначение без повторного открытия не переносит выполненную работу другому сотруднику. Повторное открытие сбрасывает завершение по существующему правилу среза. Решение закреплено регрессионным тестом аудита; согласование формулировки требований о повторном открытии остаётся отмеченным в TEST_REPORT.md.

## Как обрабатывать повреждённые ответы внешних сервисов?

Отклонять неверные типы объектов как ошибки валидации, не выдавать их за отсутствие отчёта и не сохранять успешный результат. В аудите проверены локальные ответы Kaiten, GitLab и анализатора; настоящие сервисы не вызывались.

## Как запустить Codex CLI и Claude Code, не выдавая доступ к данным сервиса?

Доверенный хост запускает одноразовый контейнер без сети и монтирований проекта. Ввод/вывод идут через stdin/stdout. Для доступа к провайдеру используется выделенный Unix-сокет CONNECT-шлюза, а не общий сетевой интерфейс. Шлюз ограничен API выбранного провайдера. Docker socket остаётся у доверенного хоста. До фактической проверки контейнеров на Linux изоляция считается подготовленной, а не подтверждённой.

## Какие учётные данные использовать для первого CLI-варианта?

CODEX_API_KEY для Codex и ANTHROPIC_API_KEY для Claude Code, только ключ выбранного провайдера. Домашние каталоги пользователя и его авторизованные сессии не копируются. Поддержка пользовательской подписки/OAuth требует отдельного способа передачи и обновления учётных данных. Ошибка не вызывает переход на API или другого поставщика.
