## Результат

### Названия выполненных и текущих задач в статистике

В нормализованной истории Bitrix сохраняется title. Локальный расчёт дополняет результат completed_tasks/current_tasks с key/title, исходные массивы ключей и counts сохраняются. HTTP-сводка передаёт эти списки, для Bitrix добавляет ссылки на задачи из sources; overdue_tasks в сводке отсутствует, просрочка остаётся counts.overdue. Для старых отчётов есть fallback на sources/task key. MCP-инструкция требует отдельно перечислять названия выполненных и текущих, просроченные показывать только количеством.

Добавлена регрессия реального локального HTTP Bitrix: завершённая с просрочкой задача даёт название в completed_tasks и overdue=1; незавершённая с просрочкой — в current_tasks и overdue=1. Проверены URL, отсутствие отдельного overdue_tasks и отсутствие задачи в противоположной категории. Существующая MCP-проверка дополнена передачей настоящего названия тестовой задачи через HTTP и Node stdio. Полный прогон: **144 теста, OK (skipped=3), 51.758 секунды** — 141 прошёл, три Unix-проверки требуют Linux. Синтаксис Python/Node проверен. Облачные модели и реальные источники при проверке не вызывались; отображение настоящей Qwen после переподключения MCP ещё требует ручной проверки.

### Статистика отделена от облачного анализа

По уточнению пользователя employee_statistics теперь строго локальна: история Bitrix → расчёт → отчёт. Не получает тексты результатов, не выполняет prepare_text, не обращается к Codex, не возвращает privacy-вопрос. Конфигурация Codex не требуется для создания такой заявки. Облачный анализ выделен в employee_review и MCP analyze_employee_work; вид заявки включён в ключ дедупликации, поэтому обычная статистика не продолжает прежнюю ожидающую облачную заявку. В Compose снята обязательная готовность Codex для запуска HTTP-сервиса.

В облачном режиме локальный вопрос содержит task_title, находки и текст «Отправить эту задачу в облачный ИИ?». MCP сопоставляет «нет»/«не отправлять»/«пропустить» с skip, «Продолжить» с continue, подставляет ID/версию текущего вопроса. Пользователю не предлагается выбирать номер вручную. В отчёте по отказу сохраняются название и причина «Задача не рассматривалась в облачном анализе: пользователь отказался от отправки данных». Само название хранится локально, в bundle передаётся лишь уже подготовленный текст.

Добавлены регрессии: статистика с неизвестной почтой проходит без маскировки/облака/загрузки результатов даже без analyzer в config; статистика и облачный анализ создают разные заявки; вопрос содержит название и отказ появляется в отчёте без отправки задачи. Полный прогон: **143 теста, OK (skipped=3), 56.465 секунды**: 140 прошли, три проверки Unix-сокета требуют Linux. Синтаксис Python/Node проверен. Реальные источники и Codex не вызывались, рабочие заявки не изменялись; поведение настоящей Qwen после обновления инструментов требует проверки в новом чате.

### Пропуск одной задачи и продолжение остальных

Проверено состояние запуска f826e0e2a8ff4dd7962da4af0b011be7 read-only: статус awaiting_privacy_decision, задачи 570/608 ожидают решения, 54/100/578/1782 имеют policy_checked. Состояний skipped нет. Показанный журнал заканчивается waiting и не подтверждает получения команды skip сервисом. Ответ Qwen и её фактический вызов инструмента в предоставленных данных отсутствуют.

Обнаружена отдельная проблема исполнения: ожидание одной задачи задерживало Codex для всех материалов. Исправлено: checked/approved задачи анализируются до возврата waiting, результат каждого сохраняется в локальном состоянии. При продолжении уже обработанные задачи повторно в Codex не отправляются. Заблокированные материалы не отправляются. Пропуск не изменяет локальные количественные показатели, но отмечает неполноту качественного анализа.

В чат показывается только первая ожидающая задача и общее число ожидающих. Решение принимается только для неё с проверкой версии; материал другой задачи изменить нельзя. Ответ содержит decision_applied со scope=single_task, task_id и action; MCP-клиент сохраняет это подтверждение после ожидания результата. Описание инструмента требует ровно один вызов на одно решение пользователя и отдельный вопрос по следующей задаче. Каждое применённое решение теперь записывается в JSONL и Docker stdout как privacy_decision, без персональных данных. Инструкция модели сама по себе не доказывает наличие согласия человека; ручная проверка поведения Qwen остаётся необходимой.

Добавлены четыре регрессии: один skip оставляет следующую задачу ожидающей, нельзя решить за ещё не показанную задачу, после skip другая проверенная задача анализируется, проверенная задача анализируется ещё до решения по проблемной и не отправляется повторно после продолжения. Полный прогон: **140 тестов, OK (skipped=3), 71.409 секунды**, лог test-run.log. 137 прошли; три проверки Unix-сокетов требуют Linux. Новых запросов к реальному Bitrix/Codex и изменений рабочего запуска агент не делал. Для применения нужна пересборка service и переподключение MCP.

## Добавленные сценарии

- Bitrix: несколько результатов, сохранение автора/даты/файлов, следующая страница; ошибка API внутри HTTP 200; некорректный повтор страницы.
- Kaiten: различие отсутствующего отчёта, ненастроенного свойства и неподдерживаемого структурированного значения; неверный тип properties.
- GitLab: короткая страница с X-Next-Page; историческая почта автора без учёта регистра; включительная нижняя и исключительная верхняя границы; collapsed; повреждённые элементы коммитов и diff.
- Транспорт: HTTP 401/403/429/500 без раскрытия тела ответа; запрет перенаправления запроса с авторизацией.
- Анализатор: пустые choices, неверная структура choice/message, незавершённый ответ.
- Статистика: переназначение после завершения не передаёт выполненную работу новому исполнителю.

## Обнаруженные и исправленные ошибки

1. Завершение учитывалось по исполнителю на конец периода. После переназначения работа первого сотрудника пропадала и могла засчитываться второму. Теперь сохраняется исполнитель на момент завершения. Повторное открытие сбрасывает завершение согласно существующему правилу.
2. Kaiten: список или строка вместо properties приводили к AttributeError; пустой список ошибочно считался отсутствием отчёта. Теперь это ошибка валидации.
3. GitLab: не-объекты в массивах коммитов/diff приводили к AttributeError. Добавлена проверка структуры и типа почты автора.
4. Анализатор: message=null приводил к AttributeError. Добавлена проверка объекта сообщения и конфигурации.
5. Во время проверки HTTP-ошибок замечен ResourceWarning. HTTPError теперь явно закрывается перед выдачей безопасной ошибки. Это дополнительное исправление по предупреждению, а не отдельный доказанный функциональный сбой.

## Форматы API по официальной документации

### Bitrix

Обычный tasks.task.result.list возвращает объект с массивом result. Элемент содержит id, taskId, createdBy, createdAt, text, formattedText, files и другие поля. files — идентификаторы, не содержимое файлов. Файл отчёта требует отдельного разрешения идентификатора и скачивания. Автор и дата должны сохраняться при объединении результатов. [Обычный REST](https://apidocs.bitrix24.com/api-reference/tasks/result/tasks-task-result-list.html).

REST 3.0 использует result.items, fileIds, authorId и другие параметры фильтрации/пагинации. Принять обёртку items недостаточно для поддержки протокола. Текущий адаптер отправляет параметры обычного REST; REST 3.0 не проверен и не считается поддержанным. [REST 3.0](https://apidocs.bitrix24.com/api-reference/tasks/result/tasks-task-result-list-rest-v3.html).

### Kaiten

Ответ получения карточки — JSON-объект. properties допускает null или объект. Ключ пользовательского свойства имеет вид id_{propertyId}; значение может быть строкой, числом, null или объектом. Это не подтверждает наличие универсального поля итогового отчёта. Сейчас разработчик задаёт report_property_id: текст поддерживается, структурированное значение помечается unsupported. Вложения как итоговые отчёты автоматически не определяются. [Документация карточки](https://developers.kaiten.ru/cards/retrieve-card).

### GitLab

Коммиты возвращаются массивом объектов с SHA id, author_email, author_name, authored_date, committed_date и другими полями. Diff — отдельный массив с old_path, new_path, diff и флагами изменения файла. collapsed/too_large доступны с GitLab 18.4. Серверный предел числа файлов может остановить выдачу: отсутствие этих флагов не гарантирует полноту diff. Тесты проверяют известные пропуски, но не доказывают полноту реальной выгрузки. [Commits API](https://docs.gitlab.com/api/commits/).
