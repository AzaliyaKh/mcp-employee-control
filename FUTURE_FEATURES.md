# Доработки для дальнейшего расширения

## Локальная проверка и маскировка персональных данных в файлах отчётов

Статус: отложено; согласовано при обсуждении первой версии.

### Что есть сейчас

В рабочей папке есть описание идеи в `idea.txt` и согласованные требования в `REQUIREMENTS.md`. Реализованы справочник и локальная маскировка обычного текста; точный статус остальных частей — в `IMPLEMENTATION_STATUS.md`. Описанная здесь проверка содержимого вложений остаётся будущей доработкой, не реализована.

- Локальный сервис напрямую вызывает API Bitrix, Kaiten и GitLab, без MCP.
- Отчёт задачи может содержать текст и файл, только файл или только текст. Несколько результатов задачи рассматриваются вместе с сохранением дат и авторства.
- Для первой версии согласованы текстовые файлы, DOCX и PDF с извлекаемым текстом. Сканы и неподдерживаемые форматы отмечаются как недоступные для анализа.
- Для файлов отчётов принято допущение об отсутствии персональных данных: отдельная проверка и маскировка содержимого вложений не предусмотрена. Это допущение, а не гарантия очистки.
- Для обычного текста предусмотрены локальная замена идентифицирующих сведений постоянными метками из справочника и остановка отправки при обнаружении оставшихся известных имён и логинов. Пользователь локально видит совпадения и выбирает: отправить показанные материалы как есть («Продолжить»), очистить фрагмент локальной Qwen с повторной проверкой («Очистить») или пропустить задачу («Пропустить»). Без ответа отправки нет.
- Код GitLab также передаётся без очистки по отдельному согласованному допущению об отсутствии в нём персональных данных и токенов.
- Локальная Qwen работает через LM Studio и плагин фиксированных функций, а сервис запускается в Docker. Способ анализа (API, Codex CLI или Claude Code) выбирает разработчик; исключение для вложений действует для всех способов.
- Справочник сотрудников хранится локально в SQLite и управляется командами добавления, импорта CSV, просмотра и редактирования. Страница управления не требуется; сотрудников не удаляем.
- Имена и соответствия авторов хранятся в локальной БД; облако получает постоянные метки, имена восстанавливаются в готовом ответе. По принятым допущениям ссылки не содержат персональных данных, а номера задач однозначны среди подключённых источников.

### Фича

Добавить локальную проверку и маскировку персональных данных в файлах отчётов до отправки в облачную модель.

### Краткое описание

Сервис извлекает текст из поддерживаемого вложения, заменяет идентифицирующие сведения по локальному справочнику и правилам, проверяет подготовленное содержимое и отправляет только проверенную версию. При невозможности прочитать или проверить файл отправка блокируется с понятной причиной. Исходный файл остаётся локально; метки позволяют восстановить имена в итоговом ответе.

При реализации определить обработку имён файлов, метаданных, таблиц и изображений внутри документов. OCR для сканов и проверку кода GitLab рассмотреть отдельно. Согласованное сохранение причины отсутствия сотрудника автоматически не пересматривать в рамках этой фичи.

### Критерии готовности

- Персональные данные в поддерживаемых вложениях заменяются до любого облачного запроса.
- Облачная модель не получает исходное вложение в обход обработки.
- Неподдерживаемые, повреждённые и непроверенные документы не отправляются.
- В отчёте различаются отсутствие вложения, ошибка чтения и блокировка проверки.

## Анализ проекта в репозитории только по данным GitLab

Статус: запланировано по запросу пользователя; реализацию не начинать в рамках добавления этой записи.

### Что есть сейчас

Есть отдельный адаптер прямого API GitLab: получение коммитов сотрудника за период и изменений кода. Полный анализ проекта в репозитории отдельной функцией сервиса и инструментом Qwen пока не реализован. Рабочий облачный сценарий сейчас получает материалы из Bitrix; точный статус — в `IMPLEMENTATION_STATUS.md`.

### Функция

Добавить самостоятельную функцию анализа проекта по ссылке или идентификатору репозитория GitLab. Пользователь сможет написать в чат, например: «Проанализируй проект group/project в GitLab: объясни архитектуру и найди проблемные места».

### Краткое описание

Qwen выбирает отдельную фиксированную функцию сервиса. Сервис получает структуру репозитория и необходимые файлы напрямую через API GitLab, подготавливает материалы, вызывает настроенный разработчиком анализатор и возвращает пояснение со ссылкой на полный отчёт. Репозиторий задаётся явно; искать его через задачи не требуется. Для анализа текущего состояния проекта справочник сотрудников не обязателен.

GitLab — единственный источник рабочих данных этого сценария. Запросы к Bitrix и Kaiten, получение постановок задач и отчётов из трекеров не выполняются. Обращение к выбранному облачному анализатору остаётся отдельным шагом; требование «только GitLab» относится к сбору данных, а не к запрету облачного анализа.

В отчёте описывать назначение проекта, структуру, основные модули, зависимости и найденные проблемы с привязкой к файлам и строкам. Состояние репозитория фиксировать по выбранной ветке и commit SHA, чтобы выводы и ссылки относились к одной версии. Историю изменений за период подключать при соответствующем запросе пользователя, а не загружать автоматически для каждого анализа.

Сохранить действующие правила подготовки исходящих данных, изоляции анализатора, хранения отчётов и журнала этапов. По принятому допущению код GitLab не маскируется; это не гарантия отсутствия в нём персональных данных и секретов. Токен GitLab анализатору не передавать. Код репозитория не запускать, зависимости проекта автоматически не устанавливать. При больших репозиториях предусмотреть анализ частями и явно указывать неполученные или необработанные материалы.

### Критерии готовности

- Функция доступна из чата отдельным инструментом; её имя и параметры согласованы между MCP и сервисом.
- Для сбора данных вызывается только API GitLab; тесты подтверждают отсутствие запросов к Bitrix и Kaiten.
- Репозиторий и версия определяются без обращения к трекерам и без обязательного выбора сотрудника.
- Выводы содержат проверяемые ссылки на файлы выбранного commit SHA; неполнота отражается в отчёте.
- Анализатор получает только подготовленные материалы, без токенов и доступа к рабочим данным сервиса.
- Результат, постоянный отчёт и журнал этапов доступны так же, как в остальных сценариях.

### Уточнить при реализации

Состав первой версии анализа: архитектура, качество кода, зависимости или отдельный вопрос пользователя; правила выбора ветки, исключения бинарных и сгенерированных файлов, ограничения объёма и стратегия разбиения большого проекта.
