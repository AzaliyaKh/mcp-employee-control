# Правила работы с проектом

Этот файл предназначен агентам разработки и действует для всего проекта. Он не загружается автоматически в локальную Qwen: её рабочие инструкции и схемы инструментов находятся в `mcp-bridge/server.mjs`.

## Перед изменениями

1. Прочитайте актуальный запрос пользователя и соответствующие части `REQUIREMENTS.md`.
2. Сверьте реализацию с `IMPLEMENTATION_STATUS.md`, последними разделами `TEST_REPORT.md` и кодом затронутых модулей.
3. Для запуска Bitrix используйте `BITRIX_LIVE.md`; для отдельных анализаторов — `analyzer/README.md`.
4. `ARCHITECTURE.md` описывает также целевую архитектуру. Старые планы тестирования, `runner/README.md` и ранние записи в документах могут описывать уже заменённые способы работы. При расхождениях учитывайте последние указания пользователя, проверяйте код и исправляйте документацию, затронутую изменением. Не объявляйте требование выполненным только потому, что оно записано в плане.

Общайтесь с пользователем по-русски, простыми словами. Пользователь разрешил самостоятельно выбирать этапы и запускать проверки: не запрашивайте подтверждение перед первым тестом или очередным обычным этапом. Неясные вопросы и принятые решения записывайте в `DECISIONS.md`. Соблюдайте границы текущего поручения и выданные разрешения.

## Назначение и обязательное разделение сценариев

Сервис помогает одному пользователю получать статистику и анализ работы сотрудников через Bionic/LM Studio с локальной Qwen. Целевая эксплуатация — Linux/Docker, текущая разработка и часть проверок — Windows/PowerShell. Отдельный чат, страница управления сотрудниками и разграничение пользовательских ролей не требуются.

### Локальная статистика

- MCP: `get_employee_statistics`; HTTP-заявка: `kind=employee_statistics`.
- Получить задачи и историю, локально рассчитать числа, сохранить отчёт и вернуть сводку со ссылкой.
- Не вызывать Codex или другую облачную модель; не выполнять маскировку и не задавать вопросы о разрешении отправки.
- Тексты итоговых результатов Bitrix для подсчёта не нужны. Сервис статистики не должен зависеть от готовности Codex.

### Облачный анализ содержания работ

- MCP: `analyze_employee_work`; HTTP-заявка: `kind=employee_review`.
- Вызывать по явному запросу качественного облачного анализа. Не добавлять облачное пояснение к обычным числам автоматически.
- Получить материалы Bitrix, обезличить обрабатываемый текст, проверить, передать подготовленные материалы изолированному Codex, проверить ответ, восстановить имена локально и сохранить отчёт.
- Текущий режим рассматривает текстовые материалы Bitrix. Полное сравнение отчёта с GitLab, чтение TXT/DOCX/PDF-вложений, проектный анализ по трём источникам и разбиение больших материалов ещё не завершены. Не выдавать текстовое пояснение Bitrix за проверку написанного кода.
- Поставщика, способ запуска и модель задаёт разработчик; модель и пользователь через чат не меняют эти настройки. Автоматической смены поставщика при ошибке нет.

## MCP и HTTP-контракты

- Сначала разрешить имя через `resolve_employee`; при нескольких кандидатах уточнить выбор.
- `employee_id` — точная метка справочника вида `EMP_001`, соответствующая `^EMP_[0-9]+$`. Не подставлять туда ФИО, логин или числовой ID Bitrix.
- Использовать точные имена из `tools/list`. Инструмента `get_employee_stats` нет.
- Без `--enable-privacy` объявлены `resolve_employee` и `get_employee_statistics`. С этим аргументом дополнительно объявлены `analyze_employee_work` и `privacy_decision`.
- Изменение инструмента согласованно затрагивает объявление, проверку аргументов и dispatch в MCP, HTTP-клиент, серверную проверку и тесты. Одного промпта недостаточно.
- Не предоставлять модели произвольные URL, пути, команды оболочки, конфигурацию анализатора или полный справочник.
- MCP stdout содержит только JSON-RPC. Служебные сообщения направлять в stderr. Отмена ожидания MCP не означает отмену уже работающей заявки сервиса.
- Числа возвращать из локального расчёта без изменения моделью. Показывать настоящую `report_url` целиком; не утверждать, что браузер открылся. Ссылка действует ограниченное время, сохранённый отчёт остаётся на диске.
- HTTP по умолчанию слушает loopback и требует технический Bearer-токен. В контейнере допускается `0.0.0.0`, порт хоста публикуется только на `127.0.0.1`.

## Персональные данные и решения пользователя

- Проверка и вопрос относятся только к материалу, который планируется отправить в облачный анализатор.
- Заменять известные текущие и исторические имена, варианты, логины, почты и телефоны. Маппинг и справочник остаются локально; облако получает только подготовленный конверт.
- Если данные остались, показать название конкретной задачи и найденные данные, затем спросить об отправке. Не требовать от пользователя искать номер: клиент берёт task_id/version из показанного вопроса.
- «Нет», «не отправлять», «пропустить» → `skip` только этой задачи. В отчёте указать её название и отказ от облачной отправки. Количественные показатели по подтверждённой истории сохраняются.
- «Продолжить» → `continue`: разрешена отправка показанной версии, включая обнаруженные данные. Решение не распространяется на другие задачи или изменённый материал.
- «Очистить» → `clean`: локальная Qwen предлагает замену, сервис повторно проверяет материал. Не выдавать исправление за автоматическое согласие на исключение.
- Показывать одну ожидающую задачу за раз. Для следующей нужен новый ответ. Молчание не разрешает отправку. Проверенные задачи продолжают обрабатываться; сохранённые ответы не запрашивать у Codex повторно после решения по соседней задаче.
- Сохранять привязку решения к задаче и версии, возвращать `decision_applied` и записывать `privacy_decision` в журнал. Инструкция Qwen не доказывает, что пользователь действительно дал согласие: не скрывать это ограничение.
- Согласованные исключения: причины отсутствия не скрываются; код GitLab и содержимое вложений предполагаются свободными от персональных данных и не очищаются в первой версии. Само чтение вложений ещё не завершено. Не заявлять гарантированную очистку всех исходящих материалов. Расширение описано в `FUTURE_FEATURES.md`.

## История и показатели

- Единый часовой пояс — Asia/Yekaterinburg, UTC+5. Даты запроса включительны; будущие изменения не должны влиять на срез прошлого периода.
- Учитывать историю назначений, завершений и дедлайнов. Не фильтровать список только по нынешнему исполнителю: это теряет переназначенные задачи. Перенос срока не должен скрывать уже состоявшееся нарушение.
- Bitrix возвращает ISO-даты и Unix timestamps. Нельзя требовать равенства task.createdDate и времени NEW: запись может быть позже.
- Нормализатор сохраняет `history_valid_from`. Период, пересекающий неизвестный промежуток до NEW, отмечается неполным; для более позднего периода использовать подтверждённую историю. Отсутствующие/повторные/противоречивые события и разрывы не исправлять догадками.
- Проверять пагинацию, повтор страниц, ограничения размеров и полноту. Превышение предела задач не превращать в успешный усечённый список. Лимит рабочего Bitrix задаётся конфигурацией, по умолчанию 1000.
- Неполноту и причины пропусков показывать явно. Ошибка одной задачи не отменяет остальные; ошибка получения общего списка или анализатора может остановить запуск.

## Данные и изоляция

- Работать внутри проекта; не менять внешние файлы, настройки приложения, VPN, домашние каталоги или системные компоненты без соответствующего поручения.
- `data/` содержит настоящие данные и секреты и исключена из Git. Не читать и не печатать её массово. Для диагностики брать только нужные поля, не выводить вебхуки, токены, auth.json, исходные документы и маппинги.
- Рабочие настройки: `data/bitrix-live/config.json`; справочник: `data/bitrix-live/private/registry.sqlite`; заявки: `private/runs.sqlite`; журналы: `logs/<run_id>.jsonl`; отчёты: `reports/<run_id>/report.json` внутри той же рабочей папки.
- База по умолчанию у employees может быть другой (`EMPLOYEES_DB` или `data/private/registry.sqlite`). Для рабочего Bitrix всегда указывать путь явно.
- `tools/prepare_bitrix_live.py` однократно копирует исходный справочник через SQLite backup. Повторный запуск не синхронизирует базы. Не заменять существующий рабочий справочник демонстрационными данными. Сотрудников не удалять, метки не перенумеровывать; сохранять историю аккаунтов, атомарность импорта и защиту от потери параллельного изменения.
- Отчёты и постоянные базы не удалять автоматически. Временные материалы хранить до решения пользователя; после окончательного завершения очищать только проверенный каталог текущего запуска. При перезапуске running становится interrupted без автоматического повтора неизвестного облачного запроса.
- Codex не должен видеть data, справочник, токены источников, Docker socket или пользовательский HOME. Рабочий daemon использует network=none, отдельные тома сокетов и авторизации и CONNECT-шлюз с ограничением доменов. Не отключать изоляцию ради прохождения теста и не подменять её запуском Codex на хосте.
- Текущая подписочная авторизация — отдельный device login в томе Codex, без копирования auth.json хоста. API-адаптеры используют свои переменные окружения. Вебхук Bitrix задаётся в окружении процесса; проект не загружает `.env` автоматически своим Python-кодом.
- Журнал: время, run_id, task_id, этап, начало/успех/ожидание/ошибка и безопасная причина. Не записывать содержимое документов или найденные персональные данные. Не делать вывод о получении команды только по словам модели — проверять состояние и подтверждение сервиса.

## Проверки и команды

Основные Python-модули используют стандартную библиотеку; отдельного шага pip install для текущего ядра нет. Не вводить новые зависимости и инфраструктуру без необходимости. Проверки сохранять на unittest; не переписывать их на pytest.

Из корня проекта:

```powershell
python -m unittest discover -s tests -v
python -m unittest discover -s tests -p 'test_bitrix*.py' -v
node --check mcp-bridge/server.mjs
node --check mcp-bridge/client.mjs
python -m compileall -q employees privacy worklog integrations analyzer tools
```

Используйте вымышленные данные, временные базы, локальные HTTP-серверы и подставные CLI. Для исправлений добавляйте содержательные регрессии: локальная статистика без облака, одна задача на решение, продолжение других задач, версии, историческое авторство, неполная история, ошибки и отсутствие секретов. Документные изменения не требуют полного прогона приложения. Три существующие проверки Unix-сокета могут пропускаться на Windows; это не подтверждение их работы на Linux. Фактическое число тестов и результаты сверять с текущим прогоном, не считать числа в старых документах неизменным контрактом.

Полезные рабочие команды:

```powershell
python -m employees --db data/bitrix-live/private/registry.sqlite list
python -m employees --db data/bitrix-live/private/registry.sqlite add
python -m employees --db data/bitrix-live/private/registry.sqlite edit EMP_001
python -m employees --db data/bitrix-live/private/registry.sqlite import data/employees.csv
python tools/diagnose_bitrix.py 54 100 1782
python tools/bitrix_logs.py
```

Реальные диагностические запросы выполняйте только в рамках задачи пользователя. Скрипт diagnose_bitrix использует работающий контейнер, выводит безопасную структуру истории и не вызывает Codex. Самостоятельные privacy/integrations-команды описаны в корневом README, analyzer-команды — в `analyzer/README.md`.

### Docker и MCP

- `compose.yaml` — офлайн-контейнер команд и проверок, network_mode=none, HTTP-сервис автоматически не запускает.
- `compose.bitrix.yaml` — рабочий HTTP-сервис Bitrix, отдельные Codex и gateway. Для интерполяции Compose нужен BITRIX_WEBHOOK_URL в текущем терминале, даже для некоторых команд просмотра. Не сохраняйте настоящий секрет в примере команды или отчёте.
- `compose.analyzer-gateway.yaml` и отдельные Dockerfile анализаторов — самостоятельные адаптеры; их готовность проверять отдельно от рабочего режима Bitrix.

```powershell
docker compose -f compose.bitrix.yaml ps
docker compose -f compose.bitrix.yaml up -d --build --no-deps service
docker logs -f --timestamps ai-service-1
docker exec ai-codex-1 codex login status
docker build -t ai-service .
python tools/run_docker_checks.py
python tools/run_bitrix_checks.py
```

Имена ai-service-1/ai-codex-1 и образ ai-service соответствуют текущему Compose-проекту ai; при другом project name берите фактические имена. Не выполнять down -v для обычного обновления: это удаляет том авторизации. Обновление исходников сервиса требует пересборки контейнера; изменение Node MCP — переподключения сервера в приложении, а после изменения схем инструментов полезен новый чат.

Если Docker Engine недоступен из среды агента, укажите фактическую ошибку, выполненные проверки и оставшиеся пользовательские шаги. Не обходите ограничения и не выдавайте config --quiet, healthy, Connected, тестовый CLI или пользовательский запуск другого пакета за успешную проверку всей цепочки с облачным Codex.

Не добавляйте новые обещания готовности по старым результатам и не объявляйте исправленным поведение Qwen, если проверен лишь серверный контракт.
