# План проверки справочника сотрудников

Статус: реализовано. Пользователь выбрал только вариант 2 — проверки через команды терминала. Проверки находятся в `tests/test_employees_cli.py`; запуск — `python -m unittest discover -s tests -v`.

Текущие проверки выполняются на Windows. Основная эксплуатация планируется на Linux; там потребуется запуск того же набора через `python3 -m unittest discover -s tests -v` и отдельная проверка контейнера.

## Интерфейсы для проверки

Согласованный интерфейс — команды employees add/list/edit/import: запуск отдельного процесса с вводом пользователя и временной базой. Проверяет диалог, отмену, сообщения, коды завершения и сохранность данных между запусками; не проверяет интеграции с трекерами, анализатором и LM Studio. Отдельных тестов Python-функций и прямых SQL-проверок нет.

## Последовательные шаги red → green

Каждый шаг начинается одним падающим тестом, затем минимальной реализацией:

1. Добавление делает сотрудника доступным через команду list с автоматически назначенной постоянной меткой.
2. Повторное открытие базы сохраняет запись и последовательность меток.
3. Редактирование меняет данные без смены метки и сохраняет исторические варианты для маскировки.
4. Конфликт внешнего аккаунта не изменяет существующие записи; одинаковые ФИО допустимы при разных аккаунтах. Resolve для модели не входит в текущую реализацию CLI.
5. Предварительный просмотр CSV показывает новые записи, дубликаты и ошибки без записи в базу.
6. Подтверждённый импорт добавляет только проверенные новые записи, не перезаписывает существующие; конфликт при применении не приводит к частичной записи.
7. Команды add/list работают в отдельных процессах с интерактивным вводом и постоянной базой.
8. Команда edit сохраняет метку; пустой ввод оставляет текущее значение, отдельный явный ввод очищает необязательное поле.
9. Команда import показывает предварительный результат и требует подтверждения; отказ не изменяет список сотрудников.

## Предлагаемые практические решения

- Использовать стандартные sqlite3, argparse, csv и unittest без внешних зависимостей.
- Путь базы: data/private/registry.sqlite; предусмотреть явный параметр для временной базы в проверках и постоянного Docker-хранилища.
- CSV UTF-8 (включая BOM), столбцы full_name, aliases, bitrix_id, kaiten_id, gitlab_username, gitlab_emails, emails, phones, logins; списки внутри ячеек разделять символом |. Метки генерировать локально, не принимать из CSV.
- ФИО обязательно; как минимум один внешний идентификатор обязателен. Аккаунты остальных систем можно заполнить позже.
- Удаление сотрудников отсутствует. Данные проверять через публичный интерфейс, не через прямые SQL-запросы в тестах.
- Docker-конфигурацию добавлять только для этого справочника, не выдавая её за готовый запуск всего приложения.

## Дополнительные выполненные проверки

- Одновременное редактирование не перезаписывает более новое изменение.
- Конфликт аккаунта при подтверждении импорта откатывает всю пачку.
- Регистр логинов и ведущие нули числовых ID не обходят проверку дубликатов.
- Повторные столбцы, повреждённые кавычки CSV и незавершённый ввод обрабатываются без сохранения сотрудников.
- Сборка Docker здесь не проверена: Docker отсутствует в текущем окружении.
